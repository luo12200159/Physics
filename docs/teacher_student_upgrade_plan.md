# 教师—学生教学闭环升级实施计划

基线：2026-10-23，分支 `feat/teacher-student-loop-v4`，源码版本 4.0.2。保留 state v10、现有题目 ID、离线作答和旧备份格式。本文记录代码事实与实施状态，不把历史 APK 版本当成源码事实。

## 现状与代码依据

- 双端是同一套 HTML/CSS/JavaScript 资源的 Android WebView 宿主，`android/tools/build_dual_android.ps1` 分别构建 student/teacher 包。Windows 复用同一 Web 源码。
- `classroom-client.js` 已有班级、邀请码、成员、作业和复核 API；服务端为 Fastify/PostgreSQL，接口在 `server/src/modules/learning/routes.ts`，数据表在迁移 `004_assignments_reviews.ts`。
- 当前 `experience-shell.js` 的学生“提交完成状态”发送状态标记而非逐题答案；服务端 `SubmissionRequestSchema` 允许空数组，教师复核列表只给 ID/状态，无法查看真实作答。这是作业闭环的首要缺口。
- 班级由服务端验证 owner/成员权限；邀请加入保留既有简单流程。尚未配置远程 HTTPS 服务时，只能在同网服务可达的条件下跨设备同步，不能把本机保存说成服务端确认。

## 最小架构调整

1. 作业发布保存题目快照（只含题干、选项、题型和知识点，不含答案），使学生设备不依赖教师本机题库；保留既有 `questionIds`。
2. 提交必须对应作业题目且包含真实答案；不可变提交版本与幂等客户端 ID 共存。教师复核可见答案、学生备注名、提交时间和历史版本；学生只能读自己的反馈。
3. 学生本机保存草稿；提交状态明确区分“本机草稿”“待同步”“服务端已确认”。断网重试使用已有同步队列，不把排队当作完成。
4. 主观题保持待人工复核；正确率分母只包含已评分证据，首次与订正分开，证据不足不下稳定能力结论。

## 风险与边界

- PostgreSQL/Redis/Docker 是否可用决定本机能否完成真实跨设备端到端验证；单元与浏览器模拟不能代替该验收。
- 旧作业可能只有题目 ID、没有题干快照；客户端只能在本机题库中解析，找不到题目时必须明确提示教师重新发布，不可伪造内容。
- 教师审核加入与历史“邀请码即申请、教师批准”保持一致；不改变学生数据归属、题目 ID 或备份结构。
- 发布前应由教师核对题目内容与授权；开发测试只使用仓库内已有示例/原创题。
